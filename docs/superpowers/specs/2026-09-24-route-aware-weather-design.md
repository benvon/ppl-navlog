# Route-aware weather design

## Purpose and scope

Issue #9 makes the current flight-planning calculation use winds and temperature aloft appropriate to each route location, altitude, and planned UTC. The planner remains a browser-local teaching tool. Pilot-entered inputs survive reload; fetched weather, calculation results, and their explanatory evidence exist only for the current successful update. A failed update retains the submitted pilot inputs and a persistent error, and removes any prior result from the current-plan view.

The active planner, Worker, domain calculation, and inspector are the implementation surface. The old single-station winds contract and `surfaceWeatherIcao` field are migration inputs, not the route-aware calculation contract. Issues #2, #3, and #4 are closed prerequisites; issue #7 supplies the input-only persistence policy. The current PDF workflow is deferred. When it is built, it needs calculated values without weather provenance or interpolation detail.

## Product behavior

The pilot sets departure UTC, route, altitudes, aircraft and fuel inputs, and optional endpoint weather-source ICAOs. Departure and destination source choices are independent. A blank choice means the endpoint airport itself, when it has an eligible four-character station ICAO; the application must not manufacture an ICAO from a three-character airport identifier. If the endpoint lacks the required report, the pilot may supply an exact alternate ICAO. The UI identifies the departure source as METAR and the destination source as TAF.

**Update plan** first saves the submitted pilot inputs, then obtains current external context and calculates. Aloft reports are selected automatically for each point's planned UTC; the pilot does not select one winds forecast period for the entire route. The API chooses the most recently issued applicable published report whose use window contains that point time. When that report covers the remaining flight, it can serve later points while it remains the newest applicable report. If it expires or a newer report becomes applicable during the flight, subsequent points use the newer applicable report. A future-issued report cannot be used before its issue time. Gaps, expired source data, or ambiguous matches make the affected estimate unavailable. Cached data cannot be treated as current after the published applicability or freshness policy ends.

The navlog shows calculated values and whether valid weather supports the current calculation. It does not display station names or annotate every change of forecast. Selecting a calculated value in the inspector shows the actual forecast sources and the horizontal, vertical, and subleg-combination math used for that value: station identities and coordinates, distances, period and issue times, levels, vector components, weights, and the calculation trace. The inspector labels a conditional TAF group as conditional. This evidence belongs to the current in-memory result and is discarded on edit, failed update, plan switch, or reload.

## Aloft point-query API

The browser sends one coordinate, altitude MSL, and planned UTC per query. It does not select winds stations, forecast periods, or interpolation methods. The Worker validates canonical input, supported region, altitude, time horizon, request size, and work limits before loading data. It returns either an estimated true wind and temperature with bounded source/method evidence or a specific unavailable/unsupported reason. This API does not fetch or resolve METAR or TAF.

The Worker uses the Aviation Weather Center winds/temps products and its station catalog. Every forecast station identifier used in geographic math must have one exact, region-consistent catalog identity with verified coordinates. Missing, duplicate, or conflicting catalog matches are rejected rather than overwritten or inferred from an ICAO/IATA convention. Catalog caching has its own validation and refresh policy. Source-product cache entries are usable only within their published use window and freshness policy; a newer applicable product supersedes an older one. Failed cycles remain explicitly unknown rather than silently absent. Existing upstream-host restrictions, response bounds, timeouts, rate limiting, and nonsensitive errors remain in force.

The Worker currently limits a decoded regional winds/temps response to 512 KiB, and that limit is a plausible cause of intermittent source failures. Before fixing a new limit, measure decoded response sizes for the supported regions and forecast cycles and use synthetic valid large-product fixtures for regression tests. The Worker must accept valid regional products larger than 512 KiB while still enforcing a finite byte, time, parse-work, and cache-size budget. Oversized and unreadable responses should have distinct internal diagnostics without exposing upstream payloads to the browser. Record the selected limit and its observed headroom; a live source request that cannot be measured is inconclusive rather than evidence that the current cap is sufficient.

Horizontal selection is deterministic and bounded by an evidence-based coverage distance. Where the station network supports interpolation, wind is interpolated in vector components and temperature as a scalar; vertical interpolation stays within published usable levels. No geographic, vertical, or time extrapolation is allowed. The answer includes actual station distances and weights, source levels and weights, product issue/use times, cache freshness, and a method identifier. Interpolated answers are disposable and are not persisted or cached as historical results.

## Route calculation

The application queries aloft at each pilot waypoint and at generated climb, descent, and altitude-transition boundaries where an aloft value applies. It adds bounded interior samples on long legs so a material wind change is not hidden by endpoint-only sampling. A sample's coordinate, altitude, and UTC come from the current estimated route geometry and timing. Adjacent sample winds are combined by documented distance/time weighting of vector components; the resulting wind affects the corresponding subleg heading, groundspeed, elapsed time, and fuel. An individual leg cannot inherit a route-wide or departure-area report solely because its altitude matches another leg.

Timing, weather-period selection, and generated phase geometry are solved with bounded deterministic iteration. The calculation converges only when route timing and phase geometry remain within documented tolerances and the selected weather periods are stable. Unsupported samples, exceeded sample/request bounds, or non-convergence block a complete navlog with a reason. Sampling spacing, station-distance bounds, iteration limits, and request limits are chosen from representative short and long routes in CONUS, Alaska, and Hawaii before being fixed in code and documented; they must not silently thin or skip required samples.

## Endpoint weather

Departure uses a fresh, identity-matched METAR from the departure airport or its explicit alternate ICAO. The existing METAR retrieval and validation path remains responsible for the observation. A surface wind used above field elevation is labeled as a planning assumption in the inspector. If the departure observation is unsuitable for the planned departure, the update fails rather than substituting aloft wind at the surface.

Destination uses a TAF from the destination airport or its own explicit alternate ICAO. A bounded Worker TAF endpoint retrieves and validates the latest issued, non-superseded TAF for that exact station; the browser uses its arrival-time forecast wind. TAF identity, issue time, validity, group times, wind units, and source freshness must be validated. The destination terminal/pattern segment uses the selected TAF wind even if an aloft estimate exists at the same altitude. Applying terminal surface forecast wind at pattern altitude is an inspector-visible planning assumption, not a claim of a measured pattern wind. No runway is selected and no runway-specific crosswind is calculated.

At planned arrival UTC, a wind-bearing `TEMPO` or `PROB` group whose period covers arrival takes precedence over the prevailing wind for this planning calculation. A conditional group without a wind retains the applicable prevailing wind. When multiple applicable conditional groups specify different winds, the application evaluates each against the arrival segment course and selects the one yielding the lowest groundspeed, which gives the highest estimated time and fuel. A stable source/group ordering breaks equal-groundspeed ties; the inspector shows the candidates, choice, and conditional nature. Forecast gusts are disclosed but are not silently substituted for mean wind in the navlog wind triangle. If group timing or selection is ambiguous, or no usable TAF covers arrival, the update fails with an explicit reason. A current METAR is never silently treated as an arrival forecast.

## Persistence, migration, and failure behavior

The v2 pilot-input document remains the only durable plan state. Departure and destination source fields save literal entered text on blur, through submissions, and after reload, including incomplete input. Existing `surfaceWeatherIcao` values map to the departure METAR choice only; destination TAF source remains unset until the pilot chooses it. Existing v1 weather/calculation snapshots, if encountered by migration or old code, cannot become current results. Removing the route-wide forecast-period selector must not erase unrelated pilot inputs.

The current result carries enough bounded, validated provenance to render its navlog and inspector consistently. Editing any pilot input invalidates that result. An Update plan attempt saves inputs before weather retrieval, shows a persistent error on any weather or calculation failure, and clears the old result. A later successful attempt replaces the error and displays only the new result. Source responses, interpolated answers, TAF/METAR payloads, and calculated output are not saved to the pilot-input database or a permanent revision archive.

## Verification and release criteria

Worker tests cover representative winds station IDs in all supported regions, exact catalog matching, conflicting coordinates, geographic and vertical interpolation, product and period selection, cache expiry/replacement, source gaps, malformed inputs, abuse limits, and clear unavailable responses. TAF tests cover exact station identity, amendments, validity, prevailing and conditional groups, group overlap, missing wind, stale data, and malformed or absent forecasts. Application tests cover distinct same-altitude route winds, long-leg interior samples, forecast-window crossing, bounded convergence, departure METAR, destination TAF at pattern altitude, conditional worst-case groundspeed selection, and blocked calculations. UI/storage tests cover separate endpoint choices, legacy single-choice migration, save/reload, failed-update persistence, subsequent recovery, and inspector evidence. The navlog and inspector must agree on the current calculation; PDF tests wait for a PDF workflow and should assert values only.

Before release, run the repository's relevant type, lint, boundary, test, build, workflow, and secret-scan gates, then exercise the local development Worker with live official-source requests and representative supported routes. Record the selected geographic/sample limits and cases where the published network cannot support an estimate. A live smoke is evidence of integration, not proof that every forecast or route is supported.
