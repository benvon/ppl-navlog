# Revisions, overrides, and weather refresh

The browser stores each plan revision as a distinct immutable journal entry. Each plan has a transaction-ordered revision number; timestamps are display metadata and never decide retention. The latest 20 entries are retained. The planner lists local plans and revisions; opening another revision requires confirmation when a revision is already open because unsaved form or draft edits may be discarded. Historical entries are read-only: saving one explicitly restores its snapshot as a new current journal entry, rather than creating a branch. The comparison view summarizes departure time, selected forecast period, aircraft profile, route points, weather evidence IDs, and calculation status. Full row-level calculations remain in each revision's inspector.

A cruise-TAS override requires an explicit unlock, an impact explanation, and a confirmation checkbox. The original aircraft default remains in the value provenance and the affected leg is visibly marked `OVERRIDDEN`. Saving the same ordered route preserves leg identities and their overrides. Changing the route structure generates new leg identities and intentionally drops leg-specific overrides so that they cannot silently apply to a different segment. Restoring a default is a separate deliberate action. A changed aircraft profile should be reviewed before recalculation.

Weather refresh starts from the current saved complete calculated revision. The pilot loads published winds periods, explicitly chooses one valid for the planned departure, and requests refresh. The application recalculates before writing anything. If weather, calculation, or immutable evidence is missing or infeasible, no new journal entry is saved and the current plan remains available. A successful refresh atomically appends a `weather-refresh` entry, new immutable source snapshots, and a bounded comparison against the immediately prior entry. New snapshot IDs and retrieval timestamps are disclosed as provenance but do not alone count as changed weather content.

Local JSON portability uses a self-contained archive for one open plan: its retained journal, aircraft profiles needed for editing, and referenced weather evidence. Reusable profiles have a separate archive. Import accepts one validated versioned archive at a time and merges new records atomically; a conflict or invalid file writes nothing. Import does not replace existing browser data, and no plan data is uploaded. A 12 MiB cap is enforced before reading and during parser validation; a save that would exceed its plan archive budget is rejected rather than creating data that cannot be restored. One-file, whole-library backup is deliberately out of scope for this pre-1.0 format.
