# Weather Model

The independent Worker exposes exact-ICAO airport lookup, METAR, winds-station discovery, and winds forecast routes under `/api/*`. It allowlists methods and routes, validates parameters, uses fixed upstream hosts, bounds time and response size, assigns a request ID, and returns structured non-sensitive errors. Airport and METAR can use compatible `runway-picker` contracts where their fields and freshness behavior meet this application’s needs.

The currently implemented airport and METAR adapter applies a five-second timeout, rejects non-successful upstream responses, limits decoded response bodies to 256 KiB, validates JSON shape and identity, and maps failures to non-sensitive 502/503 responses. It makes no network request until a configured binding receives a browser request; all tests use local fixtures and fake service fetchers.

## Official winds source and contract

V1 uses the Aviation Weather Center (AWC) Data API `GET https://aviationweather.gov/api/data/windtemp`, the official NCEP FB Winds/Temps (legacy FD) text product. AWC documents that this product provides 3,000–53,000 ft forecasts at individual three-character airport identifiers, grouped by region, at the 6-, 12-, and 24-hour forecast cycles. The Worker accepts only the documented `region`, `level=low`, and `fcst` parameters, uses the fixed `aviationweather.gov` origin, and adds an identifying User-Agent. AWC asks clients to keep requests limited and documents a 100-requests-per-minute upstream limit; the Worker relies on cache-first retrieval and its own edge rate-limit binding so browser traffic cannot directly fan out to AWC.

`GET /api/weather/winds/stations?route=<lat,lon;lat,lon...>` accepts one to 100 canonical decimal coordinate pairs. It supports a route entirely within one of the documented v1 regions: contiguous U.S. (`us`), Alaska, or Hawaii. It retrieves the three published cycle products, preserves their raw source text, then verifies the product stations’ coordinates through AWC `stationinfo` rather than inferring a location from an identifier. Its response includes all verified stations, every available valid period, the requested route, source/product metadata, and cache provenance.

`GET /api/weather/winds?station=<three-character-id>&validTime=<UTC ISO timestamp>&region=<us|alaska|hawaii>` deliberately requires the region returned by station discovery. This keeps the forecast request bounded to three cacheable upstream products. The requested valid time must exactly match a published product valid time; the Worker never substitutes the nearest forecast. Returned forecasts preserve the raw product, issue/valid/use-window timestamps, normalized altitude levels, and cache provenance.

The decoder retains original level text and normalizes the published `ddffttt` groups: direction is true degrees and speed is knots; a direction field above 50 represents 100-plus knots; `9900`, including a temperature-suffixed form such as `9900+19`, becomes a calm/light-variable 0-knot value with no fabricated direction; unavailable groups remain unavailable; and unsigned high-altitude temperatures are negative as documented by AWC. The low-level bulletin is fixed-width: blank fields at lower levels are preserved as unavailable instead of being shifted into another altitude column. Malformed headers, columns, rows, date groups, wind values, and temperatures are rejected as upstream-invalid responses rather than repaired.

V1 chooses the nearest available winds-aloft station by an explainable documented rule, then interpolates winds by altitude in vector form. Climb and descent use a sampled vector average across the applicable altitude range. The pilot selects the departure time in UTC and an available forecast-valid period explicitly; the application must not silently substitute an out-of-range forecast.

The browser-side winds adapter validates the Worker response contract before mapping it into the WX-01 through WX-04 domain models. It preserves the raw forecast, published unavailable levels, cache/source provenance, request IDs, station selection, selected use window, and every derived interpolation sample in the current calculation context. Under issue #7, these weather products and evidence are session-only and are not written to durable plan history. The adapter rejects a changed station, forecast cycle, or use window between discovery and forecast retrieval rather than combining mixed source data.

`PlanDraft` stores the pilot-selected forecast `validAt` timestamp and representative coordinate used for station selection. The low-level FB product begins at 3,000 feet, so a planned climb from the airport field needs an explicit lower anchor. When a fresh, identity-matched departure METAR provides either a fixed true wind or calm wind, the browser adapter uses the field elevation from the departure airport data—not from the METAR report—as that anchor. It vector-interpolates only from the field-elevation anchor to the first available FB level above it; all higher resolution uses the normal published-level/vector-linear rule. The current calculation context carries the raw METAR, observation time, cache/source provenance, request ID, airport-data elevation, direction treatment, first FB level, calculation trace, and user-facing planning-assumption statement. This evidence is ephemeral under issue #7.

This interpolation is deliberately unavailable, rather than silently approximated, for a variable wind, stale-cache response, missing observation time, observation later than departure or more than two hours before it, airport/METAR identity mismatch, invalid field elevation, or no FB level above the field. Calm is normalized to 000°/0 kt solely because a zero-speed vector has no directional effect, and that treatment is visible in the current calculation context. A phase that has no applied surface evidence remains bounded by published aloft levels; the application never extrapolates below its usable envelope. This is a flight-planning interpolation assumption, not a replacement for a complete weather briefing or a claim that the METAR itself contains airport elevation.

Winds products use a Cloudflare edge-cache key that includes only the fixed resource, selected region, and selected forecast cycle. They are fresh for 20 minutes and may be served only as `stale_on_error` for a maximum of two hours after retrieval. A fresh cache response is labeled `edge_hit`; an upstream retrieval is `upstream_refresh`; stale data is visibly labeled and never silently presented as fresh. Every regional winds product request has a five-second abort timeout and a 1 MiB decoded response limit; the station catalog has a separate 3 MiB decoded limit. Cache values with invalid schemas are ignored and replaced only by a validated upstream response.

Source limitations: the FB Winds/Temps product is a legacy, station-based text forecast, not a route-specific briefing, and it does not establish weather legality or replace a complete preflight weather briefing. The Worker resolves each requested point against fresh products whose published use window contains the planned UTC, then interpolates only among exact catalog identities within 200 NM. Wind is combined as east/north vector components; temperature is scalar. Altitude interpolation uses published levels only and does not extrapolate. A missing cycle, expired source, unsupported time or altitude, or point outside station coverage makes that estimate unavailable.

The initial 200 NM station limit accepts the roughly 185 NM Honolulu-to-Hilo separation in the Hawaii fixture while leaving the larger gaps in the sparse Alaska fixture unsupported. Route sampling guidance is at most 100 NM between adjacent aloft point queries; that is a conservative initial planning bound, not a validated guarantee that all material wind changes are captured. Representative short and long routes still need coverage and convergence evaluation before release.

The decoded regional product limit is 1 MiB. Development Worker measurements on 2026-09-24 were 618–12,504 bytes for supported regional cycle responses, with one Hawaii 06 request timing out once; the decoded station catalog measured 1,950,054 bytes under its separate 3 MiB cap. A valid synthetic product larger than 512 KiB is retained as a regression fixture. These measurements do not establish that a Worker upstream byte cap caused the intermittent report failure: a live discovery response was 651,267 decoded bytes and exceeded the browser client's 512 KiB response limit. Task 6 owns removal of active browser discovery. Worker point answers avoid returning the station catalog and include only bounded source evidence. Upstream byte-limit and unreadable-stream failures retain distinct internal diagnostics while returning a generic invalid-response error to the browser.
