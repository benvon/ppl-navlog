# Weather Model

The independent Worker exposes exact-ICAO airport lookup, METAR, destination TAF, winds-aloft point, and legacy winds discovery/forecast routes under `/api/*`. It allowlists methods and routes, validates parameters, uses fixed upstream hosts, bounds time and response size, assigns a request ID, and returns structured non-sensitive errors. Airport and METAR can use compatible `runway-picker` contracts where their fields and freshness behavior meet this application’s needs.

The currently implemented airport and METAR adapter applies a five-second timeout, rejects non-successful upstream responses, limits decoded response bodies to 256 KiB, validates JSON shape and identity, and maps failures to non-sensitive 502/503 responses. It makes no network request until a configured binding receives a browser request; all tests use local fixtures and fake service fetchers.

## Official winds source and contract

V1 uses the Aviation Weather Center (AWC) Data API `GET https://aviationweather.gov/api/data/windtemp`, the official NCEP FB Winds/Temps (legacy FD) text product. The supported point-query altitude is 3,000–53,000 ft; some published regional tables also contain lower levels, which the decoder preserves without widening the point-query range. Forecasts use individual three-character IATA station identifiers, are grouped by region, and have 6-, 12-, and 24-hour cycles. The Worker accepts only the documented `region`, `level=low`, and `fcst` parameters, uses the fixed `aviationweather.gov` origin, and adds an identifying User-Agent. AWC asks clients to keep requests limited and documents a 100-requests-per-minute upstream limit; the Worker relies on cache-first retrieval and its own edge rate-limit binding so browser traffic cannot directly fan out to AWC.

The legacy `GET /api/weather/winds/stations?route=<lat,lon;lat,lon...>` accepts one to 100 canonical decimal coordinate pairs. It supports a route entirely within one of the documented v1 regions: contiguous U.S. (`us`), Alaska, or Hawaii. It retrieves the three published cycle products, preserves their raw source text, then verifies product station IDs against the catalog's IATA ID field by exact equality; it never interprets product IDs as ICAO, FAA, or alias identifiers. Its response includes all verified stations, every available valid period, the requested route, source/product metadata, and cache provenance. The active planner does not call it.

The legacy `GET /api/weather/winds?station=<three-character-id>&validTime=<UTC ISO timestamp>&region=<us|alaska|hawaii>` deliberately requires the region returned by station discovery. This keeps the forecast request bounded to three cacheable upstream products. The requested valid time must exactly match a published product valid time; the Worker never substitutes the nearest forecast. Returned forecasts preserve the raw product, issue/valid/use-window timestamps, normalized altitude levels, and cache provenance.

The decoder retains original level text and normalizes the published `ddffttt` groups: direction is true degrees and speed is knots; a direction field above 50 represents 100-plus knots; `9900`, including a temperature-suffixed form such as `9900+19`, becomes a calm/light-variable 0-knot value with no fabricated direction; unavailable groups remain unavailable; and unsigned high-altitude temperatures are negative as documented by AWC. The low-level bulletin is fixed-width: blank fields at lower levels are preserved as unavailable instead of being shifted into another altitude column. Malformed headers, columns, rows, date groups, wind values, and temperatures are rejected as upstream-invalid responses rather than repaired.

The station IDs in a winds/temps product are IATA codes. Match a product ID only against the catalog's IATA ID field using exact equality; never interpret it as ICAO, FAA, or an alias. Reject the whole regional product if it repeats an ID or if a reported IATA ID has conflicting catalog identities. An ID with no exact IATA catalog match is unavailable as a station; do not interpret another identifier field as a match.

The active planner requests winds-aloft points at pilot checkpoints, generated TOC, and generated TOD, but not the destination. After TOC on a direct route, or at the final leg's origin on a multi-leg route, it places TOD once by working backward from the destination airport pattern-altitude endpoint using the latest preceding forecast. At TOD it requests a new point forecast for the descent row. The Worker resolves nearby verified stations and published altitude levels without extrapolation. Calculation is progressive: the weather sampled at A supplies the row starting at A, and the weather sampled at B supplies the row starting at B. Each answer must be valid at its requested point UTC; its published use window need not include the row's ending UTC. Each generated row recalculates course from its endpoints and magnetic variation at its midpoint and carried start time, then calculates wind correction, magnetic heading, compass deviation, compass heading, time, and fuel for that row. Each completed row carries its resulting position, altitude, UTC, fuel, and other state forward. The B answer cannot revise A→B; no final calculation reassembles or recalculates the route. The pilot does not select a forecast period for the active planner.

TOC is inserted at the planned climb-altitude crossing, receives its own point request, and supplies weather for the following interval. If departure climb reaches its accepted target at the first checkpoint, TOC is placed at that checkpoint. Checkpoint and airport pattern-altitude targets are accepted within 50 ft. When a checkpoint target is accepted during a climb or another transition allowed to end there, that phase ends at the checkpoint and carries the pilot-entered waypoint altitude forward. Backward TOD placement is checked against climb and transition endpoints before their intervals are finalized. The planner rejects a descent that would cross a pilot checkpoint before reaching the airport. TOD remains fixed after its point request; the descent row uses the sampled TOD wind and adjusts the descent rate to reach the configured airport pattern-altitude target. A required rate above 150% of the aircraft profile rate produces a planning warning while leaving the calculation available. The calculated navlog includes the airport endpoint; no fixed distance or traffic-pattern maneuver is modeled beyond it. Invalid wind, impossible groundspeed, or a descent overlapping another required transition still stops with an explanatory error.

Before fetching departure METAR or aloft weather, the planner estimates TOC and TOD with zero wind from route geometry and the entered climb/descent performance. It conservatively blocks a route when these estimates meet or cross, requiring positive cruise distance between TOC and TOD; this estimate does not prove the route is infeasible under actual wind. Wind-adjusted placement is checked again during the progressive event walk and also blocks if TOD meets or precedes the actual TOC.

After weather-adjusted TOC and TOD are known, a direct uninterrupted cruise interval of one minute or less is omitted from the navlog. Descent starts at TOC, where the generated TOD point request samples the wind used for the descent row. The required descent rate is recalculated to reach pattern altitude at the airport. This folds the short cruise interval into the descent estimate's time and fuel rather than dropping it. Cruise intervals longer than one minute remain separate. The collapse is not applied when a waypoint or another already calculated route interval lies between TOC and TOD, because moving descent back to TOC would change waypoint altitude semantics.

The primary departure airport supplies the departure METAR as the initial climb row's wind. No winds-aloft point is requested at departure and no surface-to-aloft blend is applied. The first selected cruise altitude must exceed departure field elevation so TOC is a real event. Aloft requests at pilot checkpoints use the pilot-entered inbound altitude; TOC uses the first selected cruise altitude and TOD uses the final selected cruise altitude. Altitude between waypoints is estimated to place TOC and TOD; an accepted pilot waypoint uses its entered altitude for the next row. A pilot-entered departure alternate is used only when the primary airport has no report or has no four-character ICAO identifier; a stale report or transport failure does not authorize substitution. Destination TAF and METAR are not fetched or required by the active plan update and do not change the final leg's heading, groundspeed, time, or fuel estimate. The destination target altitude must be below the final leg's cruise altitude so the route has a real descent. The plan warns when the TOD wind requires more than 150% of the profile descent rate to reach that target at the airport.

Forecast wind, aircraft performance, and fuel consumption are planning estimates. The navlog is intended to support heading and fuel-sufficiency decisions, not to predict exact future conditions. Fuel sufficiency compares estimated arrival fuel with the pilot-entered reserve threshold, reports the estimated margin or shortfall, and adds no arbitrary buffer. Navlog presentation rounds headings to the nearest whole degree, altitude to 100 ft, wind and groundspeed speeds to whole knots, distance to 0.1 NM, fuel to 0.1 gal, and ETE to whole minutes. Calculations, cumulative state, and threshold comparisons retain unrounded values; displayed rounding never feeds later intervals.

The browser validates each point response contract before using it, including rejecting stale cache states. Each aloft point answer retains source-level wind and temperature bracket values alongside their vertical and horizontal weights so the inspector can show the interpolation inputs. Current weather answers and calculation evidence are session-only under issue #7 and are not written to durable plan history. The legacy winds adapter still validates discovery and station-forecast responses when used by older flows; it rejects a changed station, forecast cycle, or use window rather than combining mixed source data.

Older `PlanDraft` records may retain a pilot-selected forecast `validAt` timestamp and representative coordinate; the active planner ignores these legacy choices. The active planner validates the selected departure METAR identity, freshness, observation time, and fixed or calm wind before calculation. It uses that wind for the departure climb row, with its own trace and source provenance. The field elevation comes from airport data rather than the METAR. A stale, future, old, mismatched, variable, or missing report stops calculation with a cause-specific message. A saved plan's Use current UTC action explicitly replaces and saves a past departure time at minute precision; it does not start a calculation. Calm is normalized to 000°/0 kt because a zero-speed vector has no directional effect. Subsequent winds-aloft samples remain bounded by published levels without extrapolation.

Winds products use a Cloudflare edge-cache key that includes only the fixed resource, selected region, and selected forecast cycle. They are fresh for 20 minutes and may be served only as `stale_on_error` for a maximum of two hours after retrieval. A fresh cache response is labeled `edge_hit`; an upstream retrieval is `upstream_refresh`; stale data is visibly labeled and never silently presented as fresh. Every regional winds product request has a five-second abort timeout and a 1 MiB decoded response limit; the station catalog has a separate 3 MiB decoded limit. Cache values with invalid schemas are ignored and replaced only by a validated upstream response.

Source limitations: the FB Winds/Temps product is a legacy, station-based text forecast, not a route-specific briefing, and it does not establish weather legality or replace a complete preflight weather briefing. The Worker resolves each requested point against fresh products whose published use window contains the planned UTC, then interpolates only among exact catalog identities within 100 NM. Wind is combined as east/north vector components; temperature is scalar when published levels support it. Altitude interpolation uses published levels only and does not extrapolate. Temperature is unavailable when no published temperature levels bracket the query altitude. A missing cycle, expired source, unsupported time or altitude, or point outside station coverage makes that estimate unavailable.

The point resolver has a 100 NM station-distance bound. The fixture's 188 NM ITO–HNL separation has a 94 NM midpoint distance to either station, while the sparse 436 NM FAI–BRW gap remains unsupported at its midpoint. These few fixture stations do not establish coverage across Hawaii, Alaska, or CONUS. The planner requests route checkpoints and generated TOC/TOD points; it does not fetch arbitrary interior route samples.

The decoded regional product limit is 1 MiB. Development Worker measurements on 2026-09-24 were 618–12,504 bytes for supported regional cycle responses, with one Hawaii 06 request timing out once; the decoded station catalog measured 1,950,054 bytes under its separate 3 MiB cap. A valid synthetic product larger than 512 KiB is retained as a regression fixture. These measurements do not establish that a Worker upstream byte cap caused the intermittent report failure: a live discovery response was 651,267 decoded bytes and exceeded the browser client's 512 KiB response limit. The active planner no longer requests discovery. Worker point answers avoid returning the station catalog and include only bounded source evidence. Upstream byte-limit and unreadable-stream failures retain distinct internal diagnostics while returning a generic invalid-response error to the browser.
