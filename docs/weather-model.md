# Weather Model

The independent Worker exposes exact-ICAO airport lookup, METAR, destination TAF, winds-aloft point, and legacy winds discovery/forecast routes under `/api/*`. It allowlists methods and routes, validates parameters, uses fixed upstream hosts, bounds time and response size, assigns a request ID, and returns structured non-sensitive errors. Airport and METAR can use compatible `runway-picker` contracts where their fields and freshness behavior meet this application’s needs.

The currently implemented airport and METAR adapter applies a five-second timeout, rejects non-successful upstream responses, limits decoded response bodies to 256 KiB, validates JSON shape and identity, and maps failures to non-sensitive 502/503 responses. It makes no network request until a configured binding receives a browser request; all tests use local fixtures and fake service fetchers.

## Official winds source and contract

V1 uses the Aviation Weather Center (AWC) Data API `GET https://aviationweather.gov/api/data/windtemp`, the official NCEP FB Winds/Temps (legacy FD) text product. The supported point-query altitude is 3,000–53,000 ft; some published regional tables also contain lower levels, which the decoder preserves without widening the point-query range. Forecasts use individual three-character airport identifiers, are grouped by region, and have 6-, 12-, and 24-hour cycles. The Worker accepts only the documented `region`, `level=low`, and `fcst` parameters, uses the fixed `aviationweather.gov` origin, and adds an identifying User-Agent. AWC asks clients to keep requests limited and documents a 100-requests-per-minute upstream limit; the Worker relies on cache-first retrieval and its own edge rate-limit binding so browser traffic cannot directly fan out to AWC.

The legacy `GET /api/weather/winds/stations?route=<lat,lon;lat,lon...>` accepts one to 100 canonical decimal coordinate pairs. It supports a route entirely within one of the documented v1 regions: contiguous U.S. (`us`), Alaska, or Hawaii. It retrieves the three published cycle products, preserves their raw source text, then verifies the product stations’ coordinates through the AWC station catalog rather than inferring a location from an identifier. Its response includes all verified stations, every available valid period, the requested route, source/product metadata, and cache provenance. The active planner does not call it.

The legacy `GET /api/weather/winds?station=<three-character-id>&validTime=<UTC ISO timestamp>&region=<us|alaska|hawaii>` deliberately requires the region returned by station discovery. This keeps the forecast request bounded to three cacheable upstream products. The requested valid time must exactly match a published product valid time; the Worker never substitutes the nearest forecast. Returned forecasts preserve the raw product, issue/valid/use-window timestamps, normalized altitude levels, and cache provenance.

The decoder retains original level text and normalizes the published `ddffttt` groups: direction is true degrees and speed is knots; a direction field above 50 represents 100-plus knots; `9900`, including a temperature-suffixed form such as `9900+19`, becomes a calm/light-variable 0-knot value with no fabricated direction; unavailable groups remain unavailable; and unsigned high-altitude temperatures are negative as documented by AWC. The low-level bulletin is fixed-width: blank fields at lower levels are preserved as unavailable instead of being shifted into another altitude column. Malformed headers, columns, rows, date groups, wind values, and temperatures are rejected as upstream-invalid responses rather than repaired.

The active planner requests one winds-aloft point for each pilot route waypoint. The Worker selects the most recently issued applicable report whose published use window contains that waypoint's planned UTC, then resolves nearby verified stations and published altitude levels without extrapolation. The browser starts with departure UTC, estimates the next waypoint arrival from the preceding leg, requests that waypoint once, corrects the leg time using both endpoint winds, and carries that time to the next leg. It then assembles the navlog and verifies that the calculated waypoint and leg times remain covered by the fetched reports. A coverage mismatch blocks the update; it does not trigger an extra point request. The pilot no longer selects a forecast period for the active planner.

The destination TAF is fetched once from the pilot-selected exact station. At calculated arrival, applicable TEMPO and PROB wind groups take precedence over prevailing wind. If several conditional winds apply, the application chooses the one that produces the lowest groundspeed on the arrival course for conservative time and fuel planning. A group without wind inherits prevailing wind. A missing, ambiguous, or unusable TAF blocks the update. The TAF surface wind is used as a stated terminal planning proxy; this feature does not select a runway.

The browser validates each point and TAF response contract before using it. Current weather answers and calculation evidence are session-only under issue #7 and are not written to durable plan history. The legacy winds adapter still validates discovery and station-forecast responses when used by older flows; it rejects a changed station, forecast cycle, or use window rather than combining mixed source data.

Older `PlanDraft` records may retain a pilot-selected forecast `validAt` timestamp and representative coordinate; the active planner ignores these legacy choices. The low-level FB product begins at 3,000 feet, so a planned climb from the airport field needs an explicit lower anchor. When a fresh, identity-matched departure METAR provides either a fixed true wind or calm wind, the planner uses the field elevation from the departure airport data—not from the METAR report—as that anchor. It vector-interpolates only from the field-elevation anchor to the first available FB level above it; all higher resolution uses the normal published-level/vector-linear rule. The current calculation context carries the raw METAR, observation time, cache/source provenance, request ID, airport-data elevation, direction treatment, first FB level, calculation trace, and user-facing planning-assumption statement. This evidence is ephemeral under issue #7.

This interpolation is deliberately unavailable, rather than silently approximated, for a variable wind, stale-cache response, missing observation time, observation later than departure or more than two hours before it, airport/METAR identity mismatch, invalid field elevation, or no FB level above the field. Calm is normalized to 000°/0 kt solely because a zero-speed vector has no directional effect, and that treatment is visible in the current calculation context. A phase that has no applied surface evidence remains bounded by published aloft levels; the application never extrapolates below its usable envelope. This is a flight-planning interpolation assumption, not a replacement for a complete weather briefing or a claim that the METAR itself contains airport elevation.

Winds products use a Cloudflare edge-cache key that includes only the fixed resource, selected region, and selected forecast cycle. They are fresh for 20 minutes and may be served only as `stale_on_error` for a maximum of two hours after retrieval. A fresh cache response is labeled `edge_hit`; an upstream retrieval is `upstream_refresh`; stale data is visibly labeled and never silently presented as fresh. Every regional winds product request has a five-second abort timeout and a 1 MiB decoded response limit; the station catalog has a separate 3 MiB decoded limit. Cache values with invalid schemas are ignored and replaced only by a validated upstream response.

Source limitations: the FB Winds/Temps product is a legacy, station-based text forecast, not a route-specific briefing, and it does not establish weather legality or replace a complete preflight weather briefing. The Worker resolves each requested point against fresh products whose published use window contains the planned UTC, then interpolates only among exact catalog identities within 100 NM. Wind is combined as east/north vector components; temperature is scalar when published levels support it. Altitude interpolation uses published levels only and does not extrapolate. Temperature is unavailable when no published temperature levels bracket the query altitude. A missing cycle, expired source, unsupported time or altitude, or point outside station coverage makes that estimate unavailable.

The point resolver has a 100 NM station-distance bound. The fixture's 188 NM ITO–HNL separation has a 94 NM midpoint distance to either station, while the sparse 436 NM FAI–BRW gap remains unsupported at its midpoint. These few fixture stations do not establish coverage across Hawaii, Alaska, or CONUS. The browser makes at most 27 point requests for the supported 25-checkpoint route, exactly one per pilot waypoint; it does not fetch interior route samples.

The decoded regional product limit is 1 MiB. Development Worker measurements on 2026-09-24 were 618–12,504 bytes for supported regional cycle responses, with one Hawaii 06 request timing out once; the decoded station catalog measured 1,950,054 bytes under its separate 3 MiB cap. A valid synthetic product larger than 512 KiB is retained as a regression fixture. These measurements do not establish that a Worker upstream byte cap caused the intermittent report failure: a live discovery response was 651,267 decoded bytes and exceeded the browser client's 512 KiB response limit. The active planner no longer requests discovery. Worker point answers avoid returning the station catalog and include only bounded source evidence. Upstream byte-limit and unreadable-stream failures retain distinct internal diagnostics while returning a generic invalid-response error to the browser.
