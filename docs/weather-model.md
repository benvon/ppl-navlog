# Weather Model

The independent Worker exposes exact-ICAO airport lookup, METAR, winds-station discovery, and winds forecast routes under `/api/*`. It allowlists methods and routes, validates parameters, uses fixed upstream hosts, bounds time and response size, assigns a request ID, and returns structured non-sensitive errors. Airport and METAR can use compatible `runway-picker` contracts where their fields and freshness behavior meet this application’s needs.

The currently implemented airport and METAR adapter applies a five-second timeout, rejects non-successful upstream responses, limits decoded response bodies to 256 KiB, validates JSON shape and identity, and maps failures to non-sensitive 502/503 responses. It makes no network request until a configured binding receives a browser request; all tests use local fixtures and fake service fetchers.

## Official winds source and contract

V1 uses the Aviation Weather Center (AWC) Data API `GET https://aviationweather.gov/api/data/windtemp`, the official NCEP FB Winds/Temps (legacy FD) text product. AWC documents that this product provides 3,000–53,000 ft forecasts at individual three-character airport identifiers, grouped by region, at the 6-, 12-, and 24-hour forecast cycles. The Worker accepts only the documented `region`, `level=low`, and `fcst` parameters, uses the fixed `aviationweather.gov` origin, and adds an identifying User-Agent. AWC asks clients to keep requests limited and documents a 100-requests-per-minute upstream limit; the Worker relies on cache-first retrieval and its own edge rate-limit binding so browser traffic cannot directly fan out to AWC.

`GET /api/weather/winds/stations?route=<lat,lon;lat,lon...>` accepts one to 100 canonical decimal coordinate pairs. It supports a route entirely within one of the documented v1 regions: contiguous U.S. (`us`), Alaska, or Hawaii. It retrieves the three published cycle products, preserves their raw source text, then verifies the product stations’ coordinates through AWC `stationinfo` rather than inferring a location from an identifier. Its response includes all verified stations, every available valid period, the requested route, source/product metadata, and cache provenance.

`GET /api/weather/winds?station=<three-character-id>&validTime=<UTC ISO timestamp>&region=<us|alaska|hawaii>` deliberately requires the region returned by station discovery. This keeps the forecast request bounded to three cacheable upstream products. The requested valid time must exactly match a published product valid time; the Worker never substitutes the nearest forecast. Returned forecasts preserve the raw product, issue/valid/use-window timestamps, normalized altitude levels, and cache provenance.

The decoder retains original level text and normalizes the published `ddffttt` groups: direction is true degrees and speed is knots; a direction field above 50 represents 100-plus knots; `9900`, including a temperature-suffixed form such as `9900+19`, becomes a calm/light-variable 0-knot value with no fabricated direction; unavailable groups remain unavailable; and unsigned high-altitude temperatures are negative as documented by AWC. The low-level bulletin is fixed-width: blank fields at lower levels are preserved as unavailable instead of being shifted into another altitude column. Malformed headers, columns, rows, date groups, wind values, and temperatures are rejected as upstream-invalid responses rather than repaired.

V1 chooses the nearest available winds-aloft station by an explainable documented rule, then interpolates winds by altitude in vector form. Climb and descent use a sampled vector average across the applicable altitude range. The pilot selects the departure time in UTC and an available forecast-valid period explicitly; the application must not silently substitute an out-of-range forecast.

The browser-side winds adapter now validates the Worker response contract before mapping it into the WX-01 through WX-04 domain models. It preserves the raw forecast, published unavailable levels, cache/source provenance, request IDs, station selection, selected use window, and every derived interpolation sample for immutable-plan snapshots. It rejects a changed station, forecast cycle, or use window between discovery and forecast retrieval rather than combining mixed source data.

Two explicit integration gaps remain. First, `PlanDraft` does not yet store the pilot-selected forecast `validAt` timestamp or the representative coordinate used for station selection, so application orchestration must require those values separately until the draft schema is extended. Second, the published low-level product begins at 3,000 feet; the adapter deliberately returns an unsupported-altitude error below its lowest available level. A future surface-METAR-to-winds-aloft blending rule must be explicitly designed, sourced, and tested before climb calculations beginning at airport elevation can use lower-altitude winds. No extrapolation is performed.

Winds products use a Cloudflare edge-cache key that includes only the fixed resource, selected region, and selected forecast cycle. They are fresh for 20 minutes and may be served only as `stale_on_error` for a maximum of two hours after retrieval. A fresh cache response is labeled `edge_hit`; an upstream retrieval is `upstream_refresh`; stale data is visibly labeled and never silently presented as fresh. Every upstream request has a five-second abort timeout and a 512 KiB decoded response limit. Station-info requests use the same bounds and are batched at no more than 100 station identifiers per request. Cache values with invalid schemas are ignored and replaced only by a validated upstream response.

Source limitations: the FB Winds/Temps product is a legacy, station-based U.S. text forecast, not a route-specific briefing, and it does not establish weather legality or replace a complete preflight weather briefing. V1 does not spatially interpolate upstream grids. It selects a verified reporting station and leaves vector altitude interpolation and phase sampling to the domain layer, preserving the station distance and source details for explanation.
