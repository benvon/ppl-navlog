# Operations

The development domain is `navlog.benvon.dev`; the planned production domain is `navlog.benvon.net`. See `docs/github-ci-cd-setup.md` for GitHub and Cloudflare configuration, `docs/release-readiness-audit.md` for milestone status, and `docs/security-review.md` for production blockers.

The Worker serves a prebuilt static artifact and exposes `GET /api/health`. Its non-sensitive response contains status, build version, commit SHA, and request ID. The UI displays a teaching-only disclaimer above the workspace and the static build identity in the page footer. Each deployed environment requires its own `AWC_COORDINATOR_API` service binding and `WEATHER_BUDGET` Durable Object namespace, plus the existing `RUNWAY_PICKER_API` and `API_RATE_LIMITER` controls. Development targets `ppl-navlog-weather-development`; production targets `ppl-navlog-weather-production`. The environments do not share counters, cached resources, cooldowns, or migration state.

CI runs type checking, linting, architecture checks, test coverage, build artifact verification, secret scanning, workflow validation, dependency auditing, and CodeQL. Pull requests never receive Cloudflare credentials or deploy. After a validated merge to `main`, the development job downloads the exact CI artifact, verifies its build identity, deploys to `navlog.benvon.dev`, smoke-tests static/API identity and a live FAA LID lookup through the `runway-picker` binding, and only then creates an RC tag and GitHub prerelease. If the live lookup fails, the deployment remains unpromoted for investigation. See `docs/github-ci-cd-setup.md` for required GitHub settings and known limits. Production deployment requires a later protected workflow, release artifact tied to the deployed SHA, documented rollback, and smoke checks.

Worker observability must be aggregate-only: request counts, latency, status/error code, upstream identity, cache status, and request ID are allowed. Do not log complete navlogs, provider tokens, or browser-local profile data.

## Aviation Weather Center operating limits

The coordinator calls only `https://aviationweather.gov/api/data/windtemp` and `https://aviationweather.gov/data/cache/stations.cache.json.gz`. It is private, has no route, workers.dev hostname, or preview URL, and accepts only fixed resource keys. Per environment, it enforces 20 provider attempts per rolling minute and 300 per day; winds are additionally limited to 288 attempts/day, each winds key to 8/6h and 32/day, and the station catalog to 4/day. These are application limits, not a provider guarantee. Development and production together could make up to 40 attempts/minute and 600/day; AWC may throttle across both applications, which is an accepted risk.

Successful winds checks are due hourly and catalog checks daily. A failed check does not extend freshness. A prior validated resource may be served for at most 120 seconds after its original refresh deadline, subject to forecast applicability and independently eligible catalog data, including its own grace interval. Beyond either resource's grace, the route returns unavailable. `fetchedAt` describes the data version; `checkedAt` describes the successful provider check. Unchanged data can have a newer `checkedAt` while retaining its `fetchedAt`. Public `upstream_refresh` cache status means navlog received a resource from the coordinator; it does not prove an AWC HTTP request occurred. Provider attempt counts must come from coordinator-declared attempt-start events, never that cache label. A service-binding request can hit coordinator storage without spending an AWC attempt.

The Worker is the CORS and policy boundary: no upstream token is exposed (none is required), the coordinator builds fixed URLs, uses a custom User-Agent, caps wind text at 1 MiB and the compressed and inflated station catalog at 3 MiB each, and aborts requests after five seconds.

Deployments must configure the Cloudflare rate-limit binding for API traffic. It enforces per-source admission; the coordinator separately owns exact rolling provider-attempt budgets, shared refresh, and fixed freshness/grace deadlines. A prior resource is unavailable after its 120-second grace expires, even if it remains in storage. An upstream outage with no eligible resource must remain a structured 503; it must not manufacture a forecast or replace a saved browser-local weather snapshot.

The Worker and coordinator must not log raw weather-product bodies, complete route query strings, client IP addresses, or browser-local planning data. Aggregate observability should cover declared provider attempts by resource kind, budget denials, joins, success/failure class, cooldowns, cache/grace outcomes, coordinator latency, and storage failures. Alert on sustained cooldowns, budget exhaustion, or coordinator failures. Do not derive provider attempt counts from public cache labels. Add the attempt-start event if absent in the deployed coordinator version.

## Coordinator deployment, local development, and recovery

The CI artifact contains static assets under `dist/` and the immutable coordinator bundle under `release-artifact/weather-coordinator/`, outside the public asset directory. Its SHA-256 manifest binds the bundle and version to `dist/version.json` and the candidate commit. Promotion verifies both before deploying the coordinator with Wrangler `--no-bundle`, then deploys the matching navlog release. Never rebuild a coordinator from a different checkout for a verified static release.

Development and production require separate environment-scoped Cloudflare deploy credentials with permission to deploy their named Worker. Keep each coordinator's SQLite migration and namespace across updates. A migration applies only to the selected environment. `npm run dev` starts Vite on port 5173, navlog on 8787, and the development coordinator on 8788 in separate local Wrangler processes. The navlog service binding reports connected to `ppl-navlog-weather-development`. A normal local winds request reaches AWC, so use `npm run test:workers` for mocked multi-Worker work; that Miniflare suite uses a fake provider and SQLite Durable Object and sends no AWC requests. The API limiter is required for all API routes; the coordinator binding is required for winds routes while airport and METAR remain runway-picker-owned.

Worker rollback must retain the same Durable Object namespace so budgets, attempt history, cooldowns, and resource versions remain authoritative. Do not roll back to the pre-coordinator direct-fetch application; use a coordinator-compatible Worker version or return unavailable while recovering. Manual edge-cache invalidation can remove only the selected environment's edge copy; it does not reset counters or force a provider request. This repository provides no deployed coordinator administration endpoint or remote Durable Object state editor. If persisted state needs repair, keep traffic unavailable as needed and use reviewed private maintenance code that preserves attempt history; do not use an invented SQL/D1 command or public reset endpoint. Inspect upstream health before clearing only explicitly approved resource state.
