# GitHub and Cloudflare setup for CI/CD

Development will be `navlog.benvon.dev`; production will be `navlog.benvon.net`. These must be separate Cloudflare Worker deployments and separate GitHub deployment environments. This document distinguishes **what works now** from **what still needs implementation** so that adding secrets does not accidentally publish an incomplete candidate.

## What works now

The repository contains `.github/workflows/ci.yml`, `codeql.yml`, and `pr-title-conventional.yml`. CI runs on pull requests and pushes to `main`; it typechecks, lints, checks architectural boundaries, runs coverage, builds static assets, scans for secrets, validates workflow pinning, and performs `npm audit`. It uploads `dist/` as a run artifact. CodeQL scans JavaScript/TypeScript on pull requests, `main`, and a weekly schedule. The PR-title workflow requires Conventional Commit syntax. CI needs no Cloudflare token. No workflow currently deploys anything.

## GitHub settings you can configure now

1. Confirm the GitHub repository's default branch is `main`. Create an active ruleset or branch-protection rule for `main`: require pull requests, at least one approval when practical, passing status checks, and disallow force pushes and deletion. Once workflows have run on a PR, select the actual checks corresponding to `validate`, `Analyze JavaScript and TypeScript`, and `conventional-pr-title` as required; use their displayed GitHub names rather than guessing. GitHub explains branch rulesets and required status checks in its [repository ruleset guide](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository).
2. Enable GitHub Actions and code scanning for the repository. Leave workflow permissions at the least privilege that supports the existing workflows: CI needs read access, while CodeQL needs `security-events: write` for uploading its analysis. Do not give general PR jobs Cloudflare credentials.
3. Create GitHub Actions environments named `development` and `production` under repository Settings → Environments. Restrict development to the trusted `main` branch (or a later explicit promotion ref); restrict production to protected release tags such as `v*` and require a reviewer where the repository plan supports it. GitHub environment rules gate jobs and make environment secrets available only after those rules pass; see [GitHub deployment environments](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments) and [environment setup](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments). Confirm your GitHub plan supports the desired protections for this repository's visibility before relying on them.

## Cloudflare prerequisites before CD is added

1. Verify that both `benvon.dev` and `benvon.net` are active Cloudflare zones in the intended account and that the `runway-picker-metar-api` Worker is available to a service binding in that account. A custom domain cannot be attached over an existing conflicting CNAME; Cloudflare can create the Worker DNS record and certificate when the custom domain is attached. See [Cloudflare Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/).
2. Choose distinct Worker names, custom domains, and rate-limit namespace IDs for development and production. Configure the rate-limit binding for `API_RATE_LIMITER` in each environment and set a policy materially below the AWC 100-requests/minute upstream ceiling, recognizing that Cloudflare's Worker rate-limit counters are per location and eventually consistent. See [Cloudflare Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/). Confirm the `RUNWAY_PICKER_API` service binding and any cache behavior in both environments.
3. Create separate least-privilege Cloudflare API tokens for development and production, scoped to the intended account and required Workers deployment resources. Do not put tokens in repository files, issue bodies, variables, or logs. Wrangler in GitHub Actions needs an API token and account ID, as documented by [Cloudflare's GitHub Actions guide](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/).
4. In each corresponding GitHub environment, add the secret `CLOUDFLARE_API_TOKEN` and the non-secret variable `CLOUDFLARE_ACCOUNT_ID`. Separate environments may use the same key names with different values, so deploy jobs must explicitly reference the correct environment. Keep the account ID out of code only for configuration hygiene; it is not a credential. Rotate a token promptly if it is exposed.

## CD implementation still required in this repository

There are **no development, preview, or production deployment workflows yet**. A future development workflow should consume the successful trusted CI artifact for the exact commit, deploy that commit's Worker and static assets to `navlog.benvon.dev`, and smoke-test build identity, static security headers, `/api/health`, rate limiting, airport/METAR service binding, and a safe winds path. Production should use a conventional versioned release from protected `main`, a validated immutable release artifact, the protected `production` environment, and smoke tests for `navlog.benvon.net`. Both workflows need concurrency controls and a tested rollback procedure. Cloudflare [Wrangler environments](https://developers.cloudflare.com/workers/wrangler/environments/) provide separate environment-specific names, bindings, and routes; configuration should be reviewed before any deploy because Wrangler configuration is the source of truth for routes and variables.

Do not add a deployment token merely because CI passes. First implement and review the CD workflows and environment-specific `wrangler.jsonc` configuration, close the open security findings in `docs/security-review.md`, and run the development smoke suite. Production promotion remains a separate later decision.
